元服务改造影响对比 — Windows 桌面工具

一、启动与准备
双击“ServiceImpact.exe”，无需安装 Python。使用 HarmonyOS / OpenHarmony 的 hdc，不支持 Android adb。
新增免费内置网络模拟：主页“配置网络环境”，选择预设后直接一键测试，自动配置手机代理并在结束后恢复。网络说明以“网络环境说明.txt”为准。本版不需要 Reqable。
电脑需已安装 hdc，手机已开启开发者模式和 USB 调试并授权这台电脑。测试期间保持手机解锁亮屏。
在“改造前”和“改造后”两组中分别填写包名。首次使用两组包名均为空，请填写已安装的应用包名。
自动获取：在手机上打开目标应用，保持解锁亮屏，在对应组点击“获取当前应用包名”。读取当前获得焦点的应用，核对前台记录、进程 UID 和安装包身份，填入该组并保存设置。再在手机打开另一版本，点击另一组的同名按钮即可。
读取时不切换手机页面、不启动测试。无法唯一识别、页面切换或连接失败时保留原输入并提示重试。桌面、锁屏、通知栏或系统弹窗可能无法识别，请打开目标应用页面。
识别到与原输入不同的包名时，清空该组旧入口、缓存目录、包文件、人工缓存值及已加载结果，防止混用；版本备注保留，请按实际情况更新。包体对比需要重新选择对应 APP/HAP。识别不会自动判断当前包属于改造前还是改造后，以你点击的组为准。
保存目录、测试方式、每种启动次数、监控时长、采样间隔、Monkey 最长秒数/最多事件/最小间隔/种子均可设置。在“设备与高级设置”中指定 hdc.exe、设备序列号和稳定等待时间；多设备时请指定序列号。
两组各自有“更多设置”设置，分别指定 Ability、模块和缓存目录；不确定入口时留空，按各自包名自动识别。

二、改造前后对比流程
1. 将两个不同包名的版本安装到同一手机。一键对比需要两个不同包名；相同包名时仍需分次更换安装版本、分别采集。工具不负责安装或切换版本。
2. 填写两组包名、操作场景、版本标签。包文件是可选的，仅用于包体大小对比；留空不影响启动、CPU、内存和缓存采集。
3. 选择测试方式：冷热启动、仅冷启动、仅热启动、随机 Monkey、冷热启动 + Monkey、仅资源监控。前三种在启动测量后追加普通资源采样；Monkey 模式在随机操作期间采样 CPU/内存，使用 Monkey 时长上限，“监控秒数”不再控制这段时长。
4. 点击“开始一键对比”。先检查两个包和入口，再依次采集改造前、停止改造前应用、采集改造后，自动生成并打开 HTML 对比报告。两组使用同一组测试参数，各自使用对应包名、入口和包文件。
5. 缓存方式默认“系统页面：测试前后自动读取”。每组先自动读取缓存，完成所选测试后再次读取并计算增长量。缓存读取、启动测量和 Monkey 运行期间不要手动操作。普通资源采样阶段可按预先约定的相同步骤操作，或仅观察首页。
6. 在“版本对比”页查看差值、变化率。报告可打印或保存 PDF。保持相同设备、网络、温度、登录态、初始数据及缓存条件；不同包名需由你确认确实对应同一业务的改造前后版本。
7. 退出后可导入两组 result.json；报告的 before_snapshot.json、after_snapshot.json 也可重新导入。
默认每种启动 10 次、监控 60 秒、间隔 5 秒。正式比较建议采集足够样本，多轮复测异常增幅。
也可通过两组各自的按钮单独采集，不同时运行。每组按自己的包名识别入口、UID、版本、系统缓存项，报告明确列出两个包名。
一键任务创建独立 batch_时间 目录，包含两组采集目录、batch.json 清单和 comparison_时间 报告目录。任一组失败或用户停止后，不再执行后续组；已有数据生成不完整报告，未执行组标为 skipped，不混用上次结果。测试前检查就失败时没有采集数据，只保存批次错误清单。
不同包名仅作为对比方式说明，不自动判定为失败；仍需确认两包确实对应同一业务的改造前后版本。若两包共享 UID，报告提示 CPU/内存可能混合统计。
相对增幅关注阈值默认 10%，可调整；它是观察提示，不是项目验收标准。

三、正式包自动缓存读取（默认）
通过系统“存储”页，按控件中的完整包名定位应用，读取独立“缓存”项。不会点击清空缓存、卸载、修改权限，也不会修改正式包。
流程：读取测试前缓存 → 冷热启动 → CPU/内存与业务场景监控 → 读取测试后缓存 → 计算后减前的增长量。
两次快照覆盖本组整个测试，包括所选的启动、普通资源监控或 Monkey 阶段。
自动读取可能需要滚动系统列表、展开“查看更多”，每次通常几十秒，最长定位 180 秒。它位于启动和资源采样之外，不计入这些指标。
读取完成后返回桌面，不重新启动被测应用。最终前后台状态不保证与测试前一致。
读取失败、未找到包名、系统布局变化、锁屏或断连会明确提示，缺失读数不会计成 0；其中一端缺失时不计算增长量。系统页面模式不会使用人工补录覆盖失败读数。
已验证适配：设置版本 7.0.0.453、中文界面、主应用实例（索引 0）。其他系统布局、语言或应用分身需另行验证，匹配失败会停止该次读取。
保留页面原文、采集时间和目标控件证据。页面 MB/KB 可能经过舍入，增长量是显示值差，不能证明不存在低于显示精度的变化。
高级设置中的“页面 KB/MB 基数”默认 1000（按单位字面含义换算），如已确认系统采用二进制标注可设为 1024；KiB/MiB 固定按 1024。非零显示单位的系统基数尚未独立校准，所以报告保留此换算假设；0 B 不受影响。两版必须使用同一基数。
报告中的系统缓存分类可能与某个 cache 目录不同，“数据”或“总计”不会被当成缓存。

四、可选：缓存目录实时监控
将缓存方式改为“缓存目录：资源阶段实时监控”，则在资源监控阶段统计 cache 目录并绘制连续趋势。
默认目录为 /data/app/el2/<用户编号>/base/<包名>/cache；其他可读目录可在高级设置中指定。
正式包的沙箱可能不可读，此模式仍会显示权限不足；推荐保持默认的系统页面模式。
目录模式没有自动缓存数据时仍可填写人工缓存开始/结束 MiB，在刷新对比、生成报告后随报告快照保存。人工值不会改写原始 result.json，也不会画成连续曲线。

五、测量口径
冷启动：强制停止目标应用并检查进程退出后启动，记录 aa start -W 的 TotalTime（到首帧）；不清数据和缓存，不代表安装后的首次启动。
热启动：保持进程，返回桌面后重新唤起，记录恢复前台耗时；会检查是否确实为热启动，异常轮次不计入均值。
包体：本地 APP/HAP 文件的字节数与 SHA256，不是安装后磁盘占用。APP 必须与 APP 比，HAP 与同模块 HAP 比；请确认文件和设备安装版本对应。
CPU：应用同 UID 可见进程的 CPU 时间增量 / 整机全部 CPU 时间增量，按整机容量 0～100% 表示；不是单核心口径。首个点或进程集合变化时没有有效 CPU 值。
内存：同 UID 可见进程 PSS Total 合计，MiB。不同 UID 的隔离渲染进程可能未计入。部分进程不可读时不把部分值冒充总值。
资源在启动测试之后单独采样，避免监控命令干扰启动计时；资源曲线不是启动瞬间的 CPU、内存曲线。
采样周期包含诊断命令开销。均值基于有效样本，峰值是采样峰值，可能漏掉瞬时峰值。启动 P95 使用最近秩法，小样本时接近最大值。
差值为改造后减改造前；CPU 差值为百分点。前值为 0 或负数时不计算相对变化率。缺失数据、设备/场景不一致、相同安装指纹、有效样本不足都会提示。

六、文件与停止
每组保存 result.json、startup.csv、resources.csv 和 logs 原始日志；未执行的阶段可能没有对应 CSV。
系统页面模式还保存 cache_snapshots.csv、logs/cache_start.json、logs/cache_end.json。结果 JSON 和报告快照包含页面原文、时间、换算基数及目标缓存控件证据。
报告目录保存 report.html、comparison.csv、comparison.json 和前后快照。HTML 可离线查看，不上传采集结果。
点击停止会取消正在等待的命令并保留已经采集的数据；Monkey 不再发送后续事件，已在设备上执行的单条动作可能稍后结束。停止或关闭工具不会恢复此前应用前后台状态。
发行版设置保存在 %LOCALAPPDATA%\ServiceImpact\impact_settings.json，采集结果保存在所选目录；建议放在可写目录。

七、随机 Monkey
实现方式：UITest 逐条随机操作，点击约 60%、滑动约 30%、返回约 10%；每条操作前检查前台 UID 和窗口，使用目标应用控件区域生成坐标。离开目标应用时尝试恢复目标，仍不匹配（如系统弹窗）则结束并记录原因。使用测试账号，随机点击可能触发业务操作。
同时填写“Monkey 最长 / 秒”和“最多事件”，任一先到即停止发起新事件。两组采用同一种子；相同种子保证生成规则一致，不保证页面路径相同。最小间隔是每条完成后的等待时间，控件检查、注入和资源诊断命令还有开销，因此实际事件速率低于简单的 1000/间隔。单次命令跨越截止时刻时，实际耗时可能略长；缓存快照和启动阶段另计。
实际事件数只计算 UITest 确认成功的随机操作，不包含恢复前台动作，也不代表业务处理成功。时长太短导致未成功注入任何事件时标为失败，不伪造次数。
日志：各组 logs/monkey_events.jsonl 保存种子、操作、序号、时间和结束原因，logs/monkey_summary.json 保存实际数量/耗时/状态。报告显示计划与实际执行信息。崩溃和 ANR 需另行使用系统诊断工具判断，本工具不提供完整稳定性判定。
兼容性选择：原生 Wukong 在部分设备上无法被普通调试进程可靠终止，因此本版本不启动原生 Wukong。设备已有 Wukong 运行时会拒绝开始随机操作，避免与其他任务相互干扰。

八、范围
用于判断改造前后启动、包体、资源占用和磁盘缓存的变化，不校验埋点事件。
本报告不能单独证明整个元服务无影响，登录、页面跳转、音视频等原业务功能仍需按实际场景回归。
当前工具未包含真实改造前后两个产物及其对比数据，需按上述流程自行采集。

源码运行：Python 3.14（含 tkinter），执行 src/impact_app.py。
构建：python scripts/build_release.py
九、在线更新
在“关于与更新”中检查正式版本，可选启动时自动检查。公开仓库无需登录或令牌。发现新版后下载 ZIP，工具核对 GitHub 返回的 SHA256 和文件大小，失败时不保留可用更新包。
下载目录为 %LOCALAPPDATA%\ServiceImpact\updates。下载完成后关闭旧版本，解压新版运行。工具不会自动执行下载内容或覆盖正在运行的程序。设置和原日志目录保留；不要删除原结果目录。
首次从旧版迁移时，可将旧 impact_settings.json 放在新版 EXE 旁；尚无新版用户设置时会读取它，保存后迁移到上述用户目录。
检查更新需要能访问 GitHub。网络失败会显示原因，不影响本地测试；首次尚无 Release 时会明确提示。
